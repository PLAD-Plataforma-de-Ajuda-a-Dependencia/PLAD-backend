# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Backend for PLAD (Plataforma de Ajuda a Dependência): a Spring Boot 4.1 / Java 25 REST API where users register as either a dependent (`dependente`) or a psychologist (`psicologo`), log in with JWT, and dependents fill out a one-time triage questionnaire. Domain vocabulary, enum values and seed data are in Portuguese.

## Commands

Use the Maven wrapper (`./mvnw` in bash, `.\mvnw.cmd` in PowerShell):

- Build: `./mvnw clean package`
- Run: `./mvnw spring-boot:run` (the API docs stay closed; add `-Dspring-boot.run.profiles=dev` to open Swagger UI at `/swagger-ui.html`)
- Image + stack: `docker build -t plad-api .` builds the multi-stage image (tests are skipped there; CI runs them). Before the first `docker compose up`, run `cp .env.example .env` (PowerShell: `Copy-Item .env.example .env`) and replace `JWT_SECRET` in it (`openssl rand -base64 48`; the example value is too short on purpose, so the app won't start with it): compose refuses to run without `DB_PASSWORD` (and the `api` without `JWT_SECRET`). `docker compose up -d --build` then starts `db` and `api`; the `api` healthcheck is `/actuator/health/readiness`. Profile `prod` (the image default) has no defaults for `DB_URL`, `DB_USER`, `DB_PASSWORD` (`ProdEnvironmentCheck` stops the start naming what is missing), `TRUSTED_PROXIES` and the rest are in `docs/deploy.md`
- Update the API contract snapshot: `./mvnw test -Dopenapi.update=true` (in PowerShell quote it: `"-Dopenapi.update=true"`, or the dot splits the argument)
- All tests: `./mvnw test` (also writes the JaCoCo coverage report to `target/site/jacoco/index.html`; the surefire `argLine` must keep `@{argLine}` or the agent is lost)
- Single test class / method: `./mvnw test -Dtest=TestDataRunner` / `./mvnw test -Dtest=TestDataRunner#savesAndFindsUserByEmail`

The app needs a running PostgreSQL at `localhost:5432/dbtest` (user/password `postgres`/`postgres`, see `src/main/resources/application.properties`). **Tests only need Docker running**: they start their own throwaway `postgres:16` via Testcontainers and never touch `pladDB` or `dbtest`. There is no in-memory test DB: `@DataJpaTest` tests use `@AutoConfigureTestDatabase(replace = NONE)`, so they hit a real Postgres with Flyway migrations applied.

Every test that loads a Spring context (`@SpringBootTest`, `@DataJpaTest`) must add `@Import(TestcontainersConfig.class)` (`src/test/java/plad/config`). It declares a single `@ServiceConnection` Postgres container shared by all contexts in the JVM, and its connection replaces `spring.datasource.*`. Unit tests with Mockito don't need it.

Running the app also needs a `JWT_SECRET` env var (at least 32 bytes, e.g. from `openssl rand -base64 48`). There is no default on purpose, so the app refuses to start without it. Export it or put it in `.env` (copied from `.env.example`, git-ignored): `application.properties` imports `.env` (`spring.config.import`, optional), the same file `docker compose` reads, and real env vars win over it. The image has no `.env` and the tests don't read it (surefire blanks `spring.config.import` and sets a throwaway `jwt.secret`).

Optional `ADMIN_EMAIL` + `ADMIN_PASSWORD` env vars create the first admin at startup (see Auth). Both or neither; the password follows the registration rule (8+ characters, at most 72 bytes) and a weaker one stops the app from starting.

Every distinct Spring context in the test JVM keeps its own Hikari pool open on the one shared Testcontainers Postgres, so adding contexts (a new `properties = ...`, `@Import` or `@MockitoBean` combination) can run it out of connections (`FATAL: sorry, too many clients already`). Prefer the default context; `AdminAccessTest` is the only one that adds its own (for the probe controller).

## Architecture

Package root is `plad` (layers: `controllers` → `services` → `repositories` → `entity`, plus `dto`, `exception`, `config`).

- **Schema is owned by Flyway**, not Hibernate: `spring.jpa.hibernate.ddl-auto=validate`. Any entity change requires a new migration `src/main/resources/db/migration/V{n}__description.sql`; never edit an already-applied migration. Triage questions are seeded via migration (V5), with `options` stored as JSONB `[{code, label}]` and `question_type` in `single_choice | multi_choice | free_text`.
- **Postgres native enums** (`user_type`, `sex`, `crm_crp_type`) map to Java enums via `@Enumerated(EnumType.STRING)` + `@JdbcTypeCode(SqlTypes.NAMED_ENUM)`. Java enum constant names must match the DB enum labels exactly (e.g. `UserType.dependente`, `Sex.nao_binario`).
- **User subtypes**: `users` is the base table; `dependents` and `psychologists` share its PK via `@OneToOne @MapsId` on `user_id`. `AuthService.register` creates the `User` plus the matching subtype row in one transaction. A `Triage` is one-to-one with a `Dependent` (`dependent_id` unique) and has `created_at` plus `updated_at` (V22; `PUT /triage` moves it, a rejected one does not); answers live in `result_questions_triages`, which allows multiple rows per question (unique index on `triage_id, question_id, md5(value_result)`, V14, so long free text doesn't hit the btree entry limit) to support multi-choice. Every triage question is optional (`required = false` for all, V15): `POST /triage` with no answers answers 204 and stores nothing (not even the `Triage` row, so the dependent can still submit later), and `PUT /triage` with no answers is a 400 `INVALID_TRIAGE` that keeps the stored triage.
- **Age**: a plataforma é só para maiores de 18 anos (`@MinAge(value = 18)` on `RegisterRequestDTO.birthDate`, for dependents and psychologists). `MinAgeValidator` gets the `Clock` bean from `config/ClockConfig` (`America/Sao_Paulo`, so "today" is the Brazilian date, not UTC); tests replace it with a fixed `Clock`. Someone born on Feb 29 turns 18 on Mar 1 in non-leap years (CC art. 132, § 3º); future dates and ages over 120 are rejected too. The `AGE_RANGE` triage question has no "under 18" option (V12).
- **Auth**: stateless JWT (jjwt). `SecurityConfig` permits `POST /auth/login`, `POST /auth/register`, `POST /auth/refresh`, `POST /auth/logout`, `/error` and the two actuator probes `GET /actuator/health/liveness` and `/readiness` by name (readiness includes the `db` indicator, liveness does not; no details; only the `health` endpoint is exposed, so `/actuator/health` and the rest answer 401) (plus `/v3/api-docs/**` and `/swagger-ui/**`, only while `springdoc.api-docs.enabled=true`) and requires auth for everything else; a missing or invalid token gets a 401 `ErrorResponseDTO` from `SecurityErrorHandler`. `JwtAuthenticationFilter` reads `Authorization: Bearer <token>` and sets the principal to the `userId` (Long) claim — controllers get the current user's ID from the principal, not an entity. The token also carries a `role` claim (the user's `type_user`: `dependente`, `psicologo`, `admin`), which the filter turns into the authority `ROLE_<VALUE>` (`ROLE_DEPENDENTE`, `ROLE_PSICOLOGO`, `ROLE_ADMIN`); `JwtService.generateToken` needs a user with a `typeUser`. `/admin/**` requires `ROLE_ADMIN` (`SecurityConfig`) and `@EnableMethodSecurity` is on, so `@PreAuthorize` works; a denial there is a 403 through `GlobalExceptionHandler#handleAccessDenied`. `admin` cannot self-register (`AuthService.register` answers 400 `INVALID_REGISTRATION`); `AdminBootstrapRunner` → `AdminBootstrapService` creates the first admin from `ADMIN_EMAIL`/`ADMIN_PASSWORD` only when both are set and the email isn't registered yet (an existing account is never promoted). Invalid tokens are ignored (request proceeds unauthenticated), and so are tokens with no `userId`, no `role` or no `tv` claim (tokens issued before those existed) or whose `tv` differs from the user's current `users.token_version` (one single-column read per authenticated request; a user that no longer exists counts as different), which makes them a 401; if that read fails the filter answers 503 `SERVICE_UNAVAILABLE` itself. `config/RateLimitInterceptor` rate-limits `/auth/login`, `/auth/register` and `/auth/refresh` per endpoint and client IP via Bucket4j (5/min, in-memory) in `RateLimiterService`; the IP is `getRemoteAddr()` as resolved by Tomcat (`server.forward-headers-strategy=native`), which honors `X-Forwarded-For` only from peers in `TRUSTED_PROXIES` (CIDR list, default private ranges). `LoginService` adds a second bucket per normalized email (10 failures per 15 min, from any IP): it takes a slot before the password check, so an exhausted bucket answers 429 without revealing whether the password was right, and gives it back on a correct login, so only failures count (`PasswordChangeService` shares this bucket, see Sessions). `RateLimiterService` picks the limit by key prefix (default 5/min; `login-email:` 10/15 min; `nickname-reroll:` 5 per fixed 24 h window) and evicts a bucket only after a full refill period of its own. Emails are stored lowercased.
- **Sessions** (refresh tokens): the access token is a 15 min JWT (`jwt.expiration-ms`, claim `tv` = `users.token_version`) in the login/refresh body; the front keeps it in memory. The refresh token is opaque (32 random bytes, URL-safe base64), stored only as its SHA-256 hex in `refresh_tokens` (V23: `user_id`, `token_hash`, `expires_at` 7 days (`auth.refresh-token.ttl-days`), `revoked_at`, `created_at`) and sent in the cookie `refresh_token` (`HttpOnly`, `Secure` (`auth.refresh-cookie.secure`, default true), `SameSite=Strict`, `Path=/auth` so the browser also sends it to logout; `RefreshCookieFactory`). `LoginController` has `POST /auth/login` (sets the cookie), `POST /auth/refresh` and `POST /auth/logout` (204, idempotent, always clears the cookie); `RefreshTokenService#rotate` revokes the token used (an atomic `UPDATE ... WHERE revoked_at IS NULL`, so of two concurrent uses only one wins) and issues a new pair. A token that is revoked and still inside its lifetime is a reuse: every active refresh token of that user is revoked and the answer is 401 `INVALID_REFRESH_TOKEN`; `rotate` has `noRollbackFor` so that revocation commits (`RefreshTokenReuseCommitTest` is the only test that proves it, because the others are `@Transactional`). Expired tokens are a plain 401, no mass revocation; a failed refresh also clears the cookie. `UserSessionService#revokeAllSessions(userId)` bumps `token_version` (atomic `UserRepository#incrementTokenVersion`; the column is `updatable = false` on the entity so a stale entity never overwrites it) and revokes the refresh tokens: that is what a password change calls. `PUT /me/password` (any role; `MeController`, `PasswordChangeService`, body `{current_password, new_password}`) is the only caller: one transaction that checks the current password, saves the new hash, calls `revokeAllSessions`, reloads the user (the call clears the persistence context, and the new access token needs the new `tv`) and starts a new session, answered 200 like the login (access token in the body, refresh cookie). So this session goes on and every other one (old access tokens, all old refresh tokens) falls. The wrong current password is 401 `INVALID_CREDENTIALS` and counts in the same `login-email:` bucket as the login (slot taken before the check, given back when the current password is right, so the 11th failure in a row is 429 and failures on both routes add up). The new password follows the registration rule (`@Size(min = 8) @MaxBytes(72)`, 400 `VALIDATION_ERROR`) and, once the current one was proven right, must differ from it (400 `INVALID_PASSWORD_CHANGE`). `/me/password` is in `SecurityConfig.CREDENTIALED_PATHS` because it sets the refresh cookie. No `AuditAction`: it is not a read of health data. `RefreshOriginFilter` (in the security chain, before `CorsFilter`) answers 403 `FORBIDDEN` to `POST /auth/refresh` and `/auth/logout` whose `Origin` is missing or not in `cors.allowed-origins`; `SecurityConfig` gives `allowCredentials` only to `/auth/login`, `/auth/refresh` and `/auth/logout` (login sets the cookie). `RefreshTokenCleanupJob` runs daily at 03:00 `America/Sao_Paulo` (`auth.refresh-token.cleanup-cron`) and deletes tokens expired or revoked more than `auth.refresh-token.cleanup-retention-days` (7) ago, logging the count. Tests that need a bearer token for a user must save a real user (`TestUsers`), because the filter reads the database.
- **Reading triages**, one route and DTO per role: psychologists read at `TriageReadController` (`/triages`: `GET /triages?page=&size=`, newest first, size 1..100, `PageResponseDTO`, and `GET /triages/{id}`, `@PreAuthorize("hasRole('PSICOLOGO')")`) and get `TriageReadResponseDTO` with `dependent {nickname, real_name}`; admins read at `AdminTriageReadController` (`/admin/triages`, `/admin/triages/{id}`, `ROLE_ADMIN`) and get `AdminTriageReadResponseDTO` with `dependent {nickname}` only. The two never share a DTO, so no `if` hides a field; the psychologist is the only role that ever sees a dependent's real name. Every psychologist and every admin reads, validated or not (`is_validate` plays no part) and as often as they want; `ROLE_DEPENDENTE` gets 403 on all four, even for their own triage (and admin on `/triages`, psychologist on `/admin/triages`), and there is no `GET /triage`. Neither shows the e-mail. `TriageReadService` is a read-write `@Transactional` (not `readOnly`: the audit entry is an INSERT), takes the reader's role from the database, loads the answers of the whole page in one query (`@EntityGraph` on the question) and records one `TRIAGE_VIEWED` per triage returned, so reading twice leaves two entries. The operations have explicit `operationId`s (`listTriages`, `findTriage`, `listAdminTriages`, `findAdminTriage`) so they do not rename `/admin/audit`'s `list` in the contract.
- **Nickname (RF007)**: every dependent gets a random anonymous nickname such as "Morcego Sereno" (animal + adjective in the animal's gender) when the account is created; psychologists get none. `NicknameGenerator` (`services/nickname`, no Spring; lists in `resources/nicknames/animals.csv` and `adjectives.csv`, guarded by `src/test/resources/nicknames/forbidden.txt`) draws with the `SecureRandom` from `NicknameConfig`, never from an id, e-mail or name. `NicknameService#assignInitial` (called by `AuthService.register` in the same transaction) and `#reroll` use `generator.claim`: up to 10 plain draws, then a number is appended ("Morcego Sereno 7"). A collision is settled by the unique constraint on `dependents.nickname` without aborting the transaction (`DependentRepository#insertWithNickname` uses `ON CONFLICT DO NOTHING`, `#updateNicknameIfFree` uses `NOT EXISTS`; both answer 0 rows on a taken nickname). Schema: V18 (nullable column + `dependent_nickname_history`), V19 (Java migration in `src/main/java/db/migration`, fills existing dependents with the same generator), V20 (NOT NULL). `POST /me/nickname/reroll` (dependent only) swaps the nickname, closes and opens the history row and writes `NICKNAME_REROLLED`; limited to 5 per dependent in a fixed 24 h window (`nickname-reroll:` bucket in `RateLimiterService`, in memory), the 6th answers 429 `RATE_LIMITED` with `Retry-After`. `GET /me` returns `nickname` for dependents. Every word on the lists is reviewed: add none without updating `docs/decisoes-para-revisao.md` (decision 7).
- **`GET /me`** (any authenticated role): `MeService#findMe` reads the user by the principal's `userId` and takes the type from the database, not from the token. `MeResponseDTO` always sends every key: `has_triage` and `nickname` are set for dependents; `real_name`, `credential_type`, `crm_crp_number` and `is_validated` for psychologists (dependents never get the real name); admin gets only the common fields; the rest are null. A token whose user no longer exists answers 401 `INVALID_CREDENTIALS`. Reading your own account writes no audit entry.
- **Consent** (LGPD art. 11): `consent.terms-version` and `consent.privacy-version` (`application.properties`, public, default `1.0`) are the versions in force. `AuthService.register` calls `ConsentService.requireCurrent` right after the admin check (missing or different `accepted_terms_version`/`accepted_privacy_version` → 400 `CONSENT_REQUIRED`, nothing created; both fields are optional in `RegisterRequestDTO` on purpose, so it is not a `VALIDATION_ERROR`) and `ConsentService.record` after the user is saved, in the same transaction: two rows in `consents` (V21: `terms` and `privacy`, version, `accepted_at`, client IP from `getRemoteAddr()`; unique per user, document and version). `POST /me/consents` (any role, 204, idempotent) accepts the versions in force; `GET /me` sends `consent_pending` (every role) while either document's current version is not on file. Old rows stay as proof. Accounts that existed before V21 and the bootstrap admin have no rows, so they show as pending: consent is never fabricated by a migration, and a pending user is not blocked. Tests simulate a new version by seeding rows of an older one (the context's properties don't change). No `AuditAction`: `consents` is itself the record.
- **Data subject rights** (LGPD art. 18): `DELETE /me` (any role but admin, body `{password}`, 204) erases the account, decision 9 is *delete, not anonymize*. `AccountDeletionService` checks the password (it spends the `login-email:` bucket like a failed login and refunds it on success; wrong → 401 `INVALID_CREDENTIALS`, admin → 403) and runs `UserRepository#deleteAccountById`, a bulk JPQL delete: `dependents`/`psychologists`, `triages` (and `result_questions_triages`), `consents`, `dependent_nickname_history` and `refresh_tokens` go through `ON DELETE CASCADE` (V24, plus V4 and V23), and the persistence context is cleared afterwards. `audit_log` is untouched on purpose (ids only, no FK, no deletes). The sessions end with the rows: refresh tokens are gone and a user that no longer exists fails the `tv` check, so nothing calls `UserSessionService`. **Every new table with a foreign key to `users` or `dependents` needs `ON DELETE CASCADE`** (or a rule of its own in decision 9): `AccountDeletionTest#everyForeignKeyToUsersOrDependentsCascades` fails otherwise, and the export and the delete tests must learn the table. `GET /me/export` (any role) is `MeExportService` → `MeExportResponseDTO`: `account`, `dependent` (nickname and its history via the read-only `DependentNicknameHistory` entity), `psychologist` (the only block with `real_name`, on `RealNameExposureTest`'s list), `consents` and `triage` with each question's text; never the password hash or a dependent's real name; no audit entry (the subject reading their own data).
- **Audit trail** (LGPD art. 11, RNF003): `audit_log` (V17) only accepts INSERT; a trigger rejects UPDATE, DELETE and TRUNCATE, and there is no FK to `users`, so the log survives account deletion. `AuditService.record(...)` is `Propagation.MANDATORY`: it fails outside a transaction, so the entry commits or rolls back together with the audited action. Actions (`AuditAction`, stored as VARCHAR): `TRIAGE_SUBMITTED`, `TRIAGE_RESUBMITTED` (written by `TriageService` only when something was stored) `TRIAGE_VIEWED` (an admin or psychologist read the triage; written by `TriageReadService`, one entry per triage returned and a new one on every read) and `NICKNAME_REROLLED` (a dependent drew a new nickname; written by `NicknameService`, the nickname itself is never in the entry). `details` holds only ids, numbers, flags and state labels: `record` rejects any other value, and text only under `actor_role`/`from_state`/`to_state` as `[a-z_]{1,30}`, so answers, names, e-mails and free text can never get in. The role of who acted goes in `details.actor_role`. `GET /admin/audit?subject_user_id=&action=&page=&size=` (admin only, newest first, size 1..100) lists the log; `GET /me/access-log` (dependent only) shows the data subject when a third party read their triage and in which role, never who (LGPD art. 18). Pages are `PageResponseDTO` (`items`, `page`, `size`, `total_elements`, `total_pages`). The audit table accepts no deletes, so tests that write to it run in a rolled-back transaction (`@Transactional`) and filter on ids of their own.
- **Errors**: every error body is `ErrorResponseDTO {code, message, timestamp, errors, trace}`, 401/403 included. `trace` is null except for `INTERNAL_ERROR`, where it holds the request id that the message tells the user to give to support. `config/RequestIdFilter` (a servlet filter at highest precedence, outside the Security chain) reads `X-Request-Id` (only `[A-Za-z0-9._-]{1,64}` is accepted, otherwise a UUID is generated), puts it in the MDC as `requestId`, echoes it in the response header and clears it afterwards; `logging.pattern.correlation` prints it on every log line. `GlobalExceptionHandler.handleUnexpected` logs stack, method and route with that id. A database that is unreachable or too slow (`CannotGetJdbcConnectionException`, `CannotCreateTransactionException`, `QueryTimeoutException`, `DataAccessResourceFailureException`, or a Hikari timeout anywhere in the cause chain) answers 503 `SERVICE_UNAVAILABLE` with `Retry-After: 5`. Services throw custom exceptions from `plad.exception`; each extends `ApiException` and fixes its `ErrorCode` in `super(...)`, and `config/GlobalExceptionHandler` maps each to an HTTP status and reads the code from the exception. New exceptions need an `ErrorCode`, a handler there and a row in the table below. `errors` is `[{field, message}]` (field in snake_case, e.g. `answers[0].values`) for `VALIDATION_ERROR` and an empty list otherwise; `message` keeps the flat `field: reason; ...` text. 401/403 are raised inside the security filter chain, before MVC, so `config/SecurityErrorHandler` (the `AuthenticationEntryPoint` and `AccessDeniedHandler` set in `SecurityConfig`) writes the same JSON. Errors that Spring maps itself (malformed JSON, unknown route, 405, 415...) use the `HttpStatus` name as the code (`BAD_REQUEST`, `NOT_FOUND`, `METHOD_NOT_ALLOWED`...). The CORS filter's 403 for a disallowed origin is Spring's own plain-text answer.

  | Code | HTTP | Origin |
  |---|---|---|
  | `VALIDATION_ERROR` | 400 | Bean Validation on `@Valid @RequestBody` (fills `errors`) |
  | `INVALID_REGISTRATION` | 400 | `InvalidRegistrationException` |
  | `INVALID_PASSWORD_CHANGE` | 400 | `InvalidPasswordChangeException` (`PUT /me/password` with a new password equal to the current one) |
  | `INVALID_TRIAGE` | 400 | `InvalidTriageException` |
  | `CONSENT_REQUIRED` | 400 | `ConsentRequiredException` (terms or privacy version missing or not the one in force, on register and `POST /me/consents`) |
  | `UNAUTHORIZED` | 401 | missing or invalid token (`SecurityErrorHandler`) |
  | `INVALID_CREDENTIALS` | 401 | `InvalidCredentialsException` (wrong e-mail or password) |
  | `INVALID_REFRESH_TOKEN` | 401 | `InvalidRefreshTokenException` (`POST /auth/refresh` with the cookie missing, unknown, expired or already used) |
  | `FORBIDDEN` | 403 | `ForbiddenActionException`, `SecurityErrorHandler` access denied, and `AccessDeniedException` from method security (`@PreAuthorize`, handled in `GlobalExceptionHandler` so it doesn't become a 500) |

- **Timestamps**: every date/time column is `TIMESTAMPTZ` (V10 converted the old `TIMESTAMP` ones, reading them as `America/Sao_Paulo`) and maps to `Instant`. `spring.jpa.properties.hibernate.jdbc.time_zone=UTC` keeps Hibernate independent of the JVM zone, and surefire runs the test JVM with `-Duser.timezone=America/Sao_Paulo` so zone bugs show up (`InstantRoundTripTest` fails if the JVM isn't in that zone). `@PrePersist` overwrites `createdAt` with `Instant.now()`, so tests can't set it.
- **API contract**: springdoc-openapi generates it and `docs/openapi.json` is the versioned snapshot that `config/OpenApiContractTest` compares with `/v3/api-docs` (normalized: sorted keys, 2-space indent, LF). Docs are closed by default (`springdoc.api-docs.enabled=false`); the `dev` profile (`application-dev.properties`) and the surefire config turn them on, and `OpenApiDisabledTest` checks they answer 401 when off. springdoc builds schemas with its own Jackson 2 mapper and ignores `spring.jackson.*`, so `OpenApiConfig` registers a `ModelResolver` with SNAKE_CASE; the test also checks real serialized keys against the schema. Document new endpoints with `@Operation`/`@ApiResponses` (errors, 401 included, use `ErrorResponseDTO`) and annotate `List` DTO fields with `@ArraySchema(arraySchema = @Schema(...))`, since a plain `@Schema` on a `List` leaks onto its items. An `OpenApiCustomizer` in `OpenApiConfig` marks every property of the response schemas (those reachable from an operation's responses) as `required`, because the API always sends every key; a response field that can be null needs `@Schema(nullable = true)` (see `ErrorResponseDTO.trace`), which keeps it required but typed nullable: the document is OpenAPI 3.1, which drops `nullable`, so the customizer renders it as `"type": ["string", "null"]`. Every operation also gets the 500 and 503 (with `Retry-After`) responses from `OperationCustomizer`s there. Every new DTO also needs a sample in `requestSamples()`/`responseSamples()` of `OpenApiContractTest`, which fails without one.
- **JSON uses snake_case** globally (`spring.jackson.property-naming-strategy=SNAKE_CASE`), so camelCase record DTO fields serialize as snake_case.

## Conventions

- Standard Java naming: PascalCase types (`UserRepository`, `UserType`, `Sex`), camelCase fields and methods (`realName`, `getRealName`), lowercase package names (`dto`). Column names stay snake_case via `@Column(name = "...")`. Only enum *constants* stay lowercase/snake_case (`dependente`, `nao_binario`, `single_choice`), since they must match the DB enum labels and the JSON values.
- DTOs are Java records with Jakarta Validation annotations; controllers use `@Valid @RequestBody`.
- Constructor injection (no `@Autowired` on fields) in main code.


## Rules

- Never edit an already-applied migration; always create a new `V{n}__...sql`.
- Never change `ddl-auto` or disable Flyway to make something work.
- Ask before adding Maven dependencies.
- Never hardcode secrets; use env vars
- `application-prod.properties` never gets a default for a credential (`${DB_URL}`, not `${DB_URL:...}`); `ProdEnvironmentCheck` and `ProdProfilePropertiesTest` pin it
- `real_name` de dependente só em DTOs de psicólogo; em qualquer outro lugar, `nickname`. Um DTO novo com `realName` entra na lista de `RealNameExposureTest`, e nunca se serializa a entidade `User`.
- New date/time columns are always `TIMESTAMPTZ`, never `TIMESTAMP`.
- After any change, run `./mvnw test` and fix failures before saying it's done.
- Every read of health data by a third party (anyone but the data subject: psychologist, admin) goes through `AuditService.record` (`TRIAGE_VIEWED` for the triage), in the same transaction as the read. `details` takes only ids and state changes, never answers, names, e-mails or free text. A new kind of access adds its own `AuditAction` and a test that the entry is written.
- Every new custom exception extends `ApiException` with its own `ErrorCode`, needs a handler in `GlobalExceptionHandler` and a row in the error code table.
- Every API contract change (endpoint, DTO field, status code, validation constraint) updates `docs/openapi.json` in the same PR: run `./mvnw test -Dopenapi.update=true`, review the diff and commit it. `OpenApiContractTest` fails until you do.
- Every PR that changes the status of a requirement (RF/RNF) updates `docs/matriz-de-requisitos.md` in the same PR: status, code location, test, and the count table at the top.
- Every new domain rule enters `docs/decisoes-para-revisao.md` in the same PR (what the system does, basis, code location, status), together with the test that pins it. Changing a decision means changing that test and its row there; keep the count table at the top in sync.

## Database

PostgreSQL 16 runs in a Docker container defined in `docker-compose.yml` at the
repo root (container name: `pladDB`, named volume `pladdb_data`). Start it with
`docker compose up -d db` (needs the `.env` from `.env.example` for `DB_PASSWORD`; plain `docker compose up` also starts the `api` service, which needs `JWT_SECRET` and takes port 8080, see `docs/deploy.md`). Only the app needs it, at `localhost:5432/dbtest`
(dev-only credentials `postgres`/`postgres`); tests use their own Testcontainers
Postgres and work with `pladDB` stopped.

If the app fails with a connection error (e.g. "Connection refused"), the
container is probably stopped. If tests fail because Docker isn't running or
reachable (Testcontainers "Could not find a valid Docker environment"), Docker
Desktop is probably stopped. In either case: stop and tell me. Do not change
code, config or credentials to work around it.
